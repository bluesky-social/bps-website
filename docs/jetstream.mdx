# Jetstream

**Jetstream** is the easiest way to get data off the [AT Protocol](https://atproto.com) network at scale.
You tell it which records you care about — posts, likes, follows, or a single
account — and it streams them back as plain JSON over one WebSocket, the moment
they happen.

You describe the slice of the network you want, and Jetstream
delivers it live, replayed from history, or both at once, all through the same
interface. The same code works whether you're building a realtime
bot or replaying a month of history into a larger application.

There are three ways to consume it:

- **Live tail** — a single WebSocket that streams events the moment they happen.
- **[Replay](/docs/jetstream-replay)** — the WebSocket plus a few HTTP calls to
  pull history, then cut over to live.
- **Snapshotting** — a point-in-time copy of the archive over HTTP, with no live
  tail.

All three come with official clients, so none of it needs hand-rolling. Start
with the live tail below.

Jetstream is [open source](https://github.com/bluesky-social/jetstream),
implemented in Go, and cheap to self-host. Read on to interact with Bluesky's public instances.

## Quickstart: live tail

Open a WebSocket to the `/subscribe` endpoint and start reading events. Add a
`wantedCollections` filter so you receive just the record types you care about:

<Tabs groupId="lang">
  <TabItem value="typescript" label="TypeScript">
    Use the [**Jetstream SDK**](/docs/jetstream-sdk):

    ```ts
    // npm install bsky-jetstream-preview — see the Jetstream SDK page.
    import { Jetstream } from 'bsky-jetstream-preview'

    const jetstream = new Jetstream('https://jetstream2.us-east.bsky.network')

    for await (const evt of jetstream.live({ collections: ['app.bsky.feed.post'] })) {
      console.log(evt)
    }
    ```
  </TabItem>
  <TabItem value="python" label="Python">
    ```python
    import asyncio
    import websockets

    uri = "wss://jetstream2.us-east.bsky.network/subscribe?wantedCollections=app.bsky.feed.post"

    async def listen():
      async with websockets.connect(uri) as ws:
        while True:
          print(await ws.recv())

    asyncio.run(listen())
    ```
  </TabItem>
  <TabItem value="shell" label="Shell">
    ```shell
    websocat "wss://jetstream2.us-east.bsky.network/subscribe?wantedCollections=app.bsky.feed.post"
    ```
  </TabItem>
</Tabs>

Each message is a self-contained JSON object. A `commit` event — someone
creating, updating, or deleting a record — looks like this:

```json
{
  "did": "did:plc:eygmaihciaxprqvxpfvl6flk",
  "time_us": 1725911162329308,
  "kind": "commit",
  "commit": {
    "rev": "3l3qo2vutsw2b",
    "operation": "create",
    "collection": "app.bsky.feed.like",
    "rkey": "3l3qo2vuowo2b",
    "cid": "bafyreidwaivazkwu67xztlmuobx35hs2lnfh3kolmgfmucldvhd3sgzcqi",
    "record": {
      "$type": "app.bsky.feed.like",
      "createdAt": "2024-09-09T19:46:02.102Z",
      "subject": {
        "cid": "bafyreidc6sydkkbchcyg62v77wbhzvb2mvytlmsychqgwf2xojjtirmzj4",
        "uri": "at://did:plc:wa7b35aakoll7hugkrjtf3xf/app.bsky.feed.post/3l3pte3p2e325"
      }
    }
  }
}
```

The record arrives already decoded in the `record` field, so there's no second
parsing step. Alongside `commit` events, the stream also carries `identity` and
`account` events (handle changes, account status) for the same accounts.

### Public endpoints

Bluesky runs two sets of public instances. The live tail works the same on
both — point any example on this page at either host — with one addition on
v2: each event also carries a `cursor` field (its sequence number; see
[Resuming](#resuming-where-you-left-off)).

| Version | Endpoint | Region |
| --- | --- | --- |
| **v2** | `wss://jetstream.us-west.bsky.network` | US West |
| **v2** | `wss://jetstream.us-east.bsky.network` | US East |
| **v1** | `wss://jetstream1.us-west.bsky.network` | US West |
| **v1** | `wss://jetstream2.us-east.bsky.network` | US East |

**Jetstream v2** is recommended for new projects. [Replay](/docs/jetstream-replay) and Snapshotting are only available on Jetstream v2. **Jetstream v1** provides legacy timestamps.

No authentication is required for the live tail; these
instances serve the full network, and your `wantedCollections` / `wantedDids`
filters decide how much of it reaches you.

## Filtering: ask for just your slice

Filtering happens server-side, so a narrow filter means less bandwidth and less
work for your client. Two filters are available, and they combine:

- **`wantedCollections`**: one or more [NSIDs](https://atproto.com/specs/nsid).
  Repeat the parameter for multiple collections. Prefixes work too, so
  `app.bsky.feed.*`-style scoping lets you take a whole namespace.
- **`wantedDids`**: restrict the stream to specific accounts by DID. Repeat for
  multiple accounts.

```
wss://jetstream2.us-east.bsky.network/subscribe
  ?wantedCollections=app.bsky.feed.post
  &wantedCollections=app.bsky.feed.like
  &wantedDids=did:plc:eygmaihciaxprqvxpfvl6flk
```

:::tip Long filter lists
If you're filtering on a large or changing set of collections or DIDs, send them
in a `options_update` message after connecting (set `requireHello=true` on the
URL to suppress events until your first update arrives) rather than stuffing
everything into the query string.
:::

## Resuming where you left off

On **v2** instances, every event carries a `cursor` — a monotonically
increasing sequence number. If your consumer drops, reconnect with `?cursor=N`
(the last value you processed) and Jetstream replays from there, within a
bounded lookback window:

```
wss://jetstream.us-east.bsky.network/subscribe?wantedCollections=app.bsky.feed.post&cursor=12345
```

The cursor is **inclusive** — you'll receive event `N` itself again — and
delivery is **at-least-once**, so an event may arrive more than once across a
reconnect. Make your handlers idempotent. Key on each record's `at://` URI and
duplicates become harmless.

On **v1** instances there is no `cursor` field: use an event's `time_us`
(microsecond timestamp) as the `?cursor=` value instead. v2 accepts both kinds
of cursor on the same parameter, so a v1-style consumer keeps working after
pointing at a v2 host.

## Getting history, not just live

The cursor window above is meant for short reconnects, not for loading the past.
When you also need historical data — say, every `app.bsky.feed.post` from the
last month, then live updates from there — Jetstream **replays** the archive over
HTTP and cuts over to this live tail at the tip. The server holds the archive, so
there's nothing to stage on your side; your code never has to know whether a
given event is history or real time.

That's the **[Network Replay](/docs/jetstream-replay)** path. It uses the same
filters as the live tail and adds a few authenticated HTTP calls to pull the
history.

## How Jetstream relates to the firehose

Under the hood, Jetstream consumes the network's full
[firehose](/docs/consuming-the-firehose) from a [Relay](/docs/relay) and does
the decoding and filtering so you don't have to.
You only need the raw firehose directly when you want something Jetstream
deliberately trades away for simplicity:

| | Jetstream | [Relay firehose](/docs/consuming-the-firehose) |
| --- | --- | --- |
| Encoding | **JSON**, already decoded | binary (DAG-CBOR + CAR) |
| Filtering | by **collection** and/or **DID** | none; you get everything |
| History | **live, historical, or both** | live only |
| What you run | a WebSocket client | a CBOR/CAR decoder, cursor logic |

Use the [raw firehose](/docs/consuming-the-firehose) when you need every
record with no filtering, or the cryptographic proofs to verify repository state
yourself. For nearly everything else, Jetstream is the simpler path.

## Running your own Jetstream

The public instances are enough for most consumers. If you'd rather run your
own, Jetstream is a single static Go binary that archives the network to local
disk and serves the same live tail, replay, and snapshot endpoints as the
public instances. **[Running your own
Jetstream](/docs/jetstream-self-host)** covers what to expect: the initial
backfill, hardware, configuration, and how to gate the expensive replay
endpoints the way Bluesky's instances do.
